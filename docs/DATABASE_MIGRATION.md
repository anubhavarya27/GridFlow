# MySQL → PostgreSQL/TimescaleDB migration

Source: U/BILL MySQL 8 scripts, kept unchanged in
[`database/legacy-mysql/`](../database/legacy-mysql) (01–09). Target: PostgreSQL 16 +
TimescaleDB, [`database/postgres/`](../database/postgres) (00–09, 99).

The original MySQL database is **never modified or deleted** by any GridPulse script.
The only addition to it is the optional `legacy-mysql/10_benchmark_interval_readings.sql`
table used by the Performance Lab baseline.

## 1. Conversion rules

| MySQL (U/BILL) | PostgreSQL (GridPulse) | Why |
|---|---|---|
| `CREATE DATABASE … ; USE …` | `00_roles_and_database.sql` creates roles and DB `gridpulse` | PG has no `USE`; connect with `-d` |
| Mixed-case names (`Customer`, `CUSTOMER`) | unquoted, folded to lower case (`customer`) | existing SQL such as `FROM Customer` and `FROM CUSTOMER` still works |
| `INT` / `DECIMAL(p,s)` | `INTEGER` / `NUMERIC(p,s)` | equivalent exact types |
| `AUTO_INCREMENT` (app tables) | `GENERATED BY DEFAULT AS IDENTITY` (`ALWAYS` for new tables) | domain tables had none — their IDs are business keys and stay user-supplied |
| `ENUM('A','B')` | `VARCHAR` + `CHECK (col IN (...))` | portable, same validation |
| `JSON` | `JSONB` | indexable, validated |
| `DATETIME` | `TIMESTAMPTZ` | stores an instant; presentation in Asia/Kolkata |
| `ON UPDATE CURRENT_TIMESTAMP` | `BEFORE UPDATE` trigger `set_updated_at()` | PG has no column-level ON UPDATE |
| `TINYINT(1)` | `BOOLEAN` | |
| inline `INDEX` in `CREATE TABLE` | separate `CREATE INDEX` | PG syntax |
| InnoDB auto-indexes FK columns | explicit indexes on FK columns used in joins | PG does not create them |
| `DATE_FORMAT(d,'%Y-%m')` | `to_char(d,'YYYY-MM')` | in backend queries |
| backtick identifiers | double quotes (rarely needed now) | Query Studio generator updated |
| `SHOW COLUMNS FROM t` | `GET /api/query/schema/{table}` (information_schema, MySQL-shaped result) and `DESCRIBE t` translation | Query Studio record forms keep working |
| `multipleStatements: true`, root connection | one statement per read, restricted roles | security (see API contract) |

All 20 domain tables keep their **primary keys, composite keys, UNIQUE constraints,
foreign keys (with the same ON UPDATE/ON DELETE actions) and CHECK constraints, with the
same constraint names**.

## 2. Schema review — corrections made

Each is marked `[GRIDPULSE]` in the SQL.

| # | Finding in U/BILL | Change | Effect on legacy data |
|---|---|---|---|
| 1 | `bill.billing_month` is a DATE meant to identify a month, nothing enforced the 1st | `CHECK (billing_month = date_trunc('month', billing_month))` | all 30 legacy bills already comply |
| 2 | Nothing prevented two cycle readings for the same meter and date | `UNIQUE (meter_id, reading_date)` on `meter_reading` | complies |
| 3 | `QUERY_REQUEST.status` lifecycle existed only in docs/code | `CHECK` on the six states | complies |
| 4 | FK columns unindexed after the move to PG | 7 FK indexes | none |
| 5 | `users.password_hash` stored the admin hash copied from `.env` | `app_users` has **no password column**; demo passwords come from configuration only | passwords are not migrated (`--include-app-tables` copies usernames/roles only) |
| 6 | No unit of measure anywhere in the model | derived in `v_meter_profile`: electricity → **kWh**, water → **kL** | documented assumption |
| 7 | No bill amount stored or computed in the API | derived (not stored) by `TariffCalculator`, see [BILLING_RULES.md](BILLING_RULES.md) | none |

### Inconsistencies found in the legacy sample data (not edited)

| Finding | Where reported |
|---|---|
| Payment 9008 has `payment_mode = 'UPI'` but its specialization row is in `CARD_PAYMENT` | `99_validation.sql` WARN |
| The 18 legacy "Paid" bills: the payment amounts do not equal any amount formula present in the data (e.g. bill 5001: 150 units × ₹8.50 = ₹1,275; with fixed charge and 5 % tax ₹1,391.25; paid ₹1,320) | WARN; bill 5001 shows a balance due of ₹71.25 |
| `reportController.js` / several U/BILL controllers used upper-case table names (`FROM CUSTOMER`), which fail on MySQL servers with case-sensitive table names (Linux default) | fixed by PG case folding |

Changing historical records would hide these issues, so they are reported, not "fixed".

## 4. Migration procedures

### A. Fresh install with the original sample data (no live MySQL needed)

`06_legacy_data.sql` contains the U/BILL sample data converted to PostgreSQL syntax
(values unchanged). `docker compose up -d` runs 00–08 automatically.

### B. Copy a live U/BILL MySQL database

```bash
pip install PyMySQL "psycopg[binary]"
export MYSQL_HOST=localhost MYSQL_USER=gridpulse_ro MYSQL_PASSWORD=... MYSQL_DATABASE=utility_billing_db
export PGHOST=localhost PGUSER=gridpulse_app PGPASSWORD=... PGDATABASE=gridpulse
python3 database/migration/migrate_mysql_to_postgres.py migrate --replace [--include-app-tables] [--include-interval]
python3 database/migration/migrate_mysql_to_postgres.py verify      # read-only re-check
```

`migrate` runs in **one PostgreSQL transaction**: copy the 20 domain tables in FK order →
verify → commit, or roll back if anything differs. MySQL is only read.

Verification performed by the script:

1. row counts per table, MySQL vs PostgreSQL;
2. a SHA-256 fingerprint over every row of every table (normalized values);
3. per-bill units (`current − previous`) and per-bill payment totals;
4. orphan checks (payments without bills, bills without meters, readings without meters,
   card payments without payments).

### C. Generated time series

The legacy data has three readings per meter, which is not a time series. The generator
(`database/generator/generate_dataset.py`) produces a reproducible, **clearly labelled
simulated** dataset (`data_source = 'SIMULATED'`): 15-minute readings for the 10 legacy
meters from 1 Jan 2025, anchored so the register at 1 Jan / 1 Feb / 1 Mar 2025 equals the
legacy `METER_READING` values exactly, plus later bills (≥ 5031) and payments (≥ 9020).
`scripts/load_generated_postgres.sql` and `scripts/load_generated_mysql.sql` load the same
CSV files into both databases so the Performance Lab compares identical data.

## 6. Cut-over checklist

1. Back up MySQL (`mysqldump`) — keep the old database running during development.
2. Bring up PostgreSQL + TimescaleDB and run 00–08.
3. `migrate --replace` (or use the bundled sample data); keep the verification output.
4. Load or capture interval readings; run `09_post_load.sql`.
5. `99_validation.sql` → no FAIL.
6. Point the backend `.env` at PostgreSQL; run `node backend/scripts/api-smoke-test.mjs`.
7. Only then stop using the MySQL-backed U/BILL. Keep MySQL read-only for the Performance Lab.
